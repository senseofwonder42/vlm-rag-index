# Multi-document filesystem

The PageIndex idea, applied one level up: a corpus is a tree the agent navigates. This document specs the design and the v1→v2 boundary.

## The problem

A real corpus is some mix of:

- Folder structure imposed by humans (sometimes meaningful, often not).
- Document filenames (sometimes meaningful, often not).
- Document content (always meaningful, expensive to read).

Vector RAG flattens all of this into chunks and treats relevance as cosine similarity, throwing away the structural signal that already exists and forcing the system to recover it through reranking or graph hacks. This project keeps the structure as a tree and lets the agent navigate it.

## Three mechanisms

From the [PageIndex Filesystem blog post](https://pageindex.ai/blog/pageindex-filesystem), made concrete:

### Virtual nodes

When the on-disk hierarchy is flat or its labels carry no semantic signal (`docs/`, `uploads-2024/`), synthesize a hierarchy from per-document metadata. The metadata is a sidecar JSON, `<doc>.meta.json`, written at index time by one LLM call per document, prompted with the document's top-level summaries:

```json
{
  "doc_name": "annual_report_2023.pdf",
  "category": ["financial reporting", "annual"],
  "entities": ["Acme Corp", "FY2023"],
  "summary": "Acme Corp's 2023 annual report covering operations, financials, and forward-looking statements.",
  "keywords": ["revenue", "operating margin", "guidance"],
  "schema_version": 1
}
```

A document can live under multiple virtual ancestors — `category` is a list and `entities` define orthogonal axes. The tree the agent sees is a *projection* of this metadata, not a fixed hierarchy.

### Query-dependent trees

The corpus tree is not stored. It is built at query time from the metadata store. The build pipeline:

1. Reads `*.meta.json` from `index_results_dir`. Small files; cheap.
2. Picks one or two axes most relevant to the query (`category`, `entities`, free-form) by asking the LLM: "Given these axes and this question, which axes will best discriminate relevant documents?" One small call.
3. Bins documents by the chosen axes.
4. Returns a shallow tree (depth 2–3, typically) tailored to the question.

Trees are not cached across queries — they are cheap to rebuild and stale caches cause silent retrieval misses.

### Adaptive traversal

Once a tree exists, the agent descends it. At each node, the policy is:

- **If child labels carry information that discriminates relevant from irrelevant for this query**, descend layer by layer.
- **If they don't** — every child looks equally plausible — flatten: take the union of grandchildren and decide at that level.

The decision is made by the agent itself via a prompt that lists the children and asks "Which of these is most relevant to the question, or is the distinction at this level unclear?". Flattening is just "all of the above" as the answer. The recursion is bounded by `filesystem_max_tree_depth` plus an LLM-call budget per query (see open questions).

## Data model

Three files per indexed document, all in `index_results_dir`:

- `<doc>.pdf` — the source.
- `<doc>.json` — the `IndexResult` (single-doc index tree).
- `<doc>.meta.json` — the sidecar (multi-doc metadata).

No global corpus database. The `meta.json` files *are* the corpus index. Adding a document means dropping its three files into the directory; removing one means deleting them. The system is stateless above the per-document level.

## v1 → v2 boundary

The metadata sidecar is generated by v1's indexer (Phase 3 in [ROADMAP.md](ROADMAP.md)) but not consumed by the v1 agent tools. This means the corpus is filesystem-ready *before* the agent learns to use it.

The v2 cutover is purely an agent-side change:

- Add `pageindex/filesystem/{store,virtual_nodes,traversal}.py`.
- Add three tools to `agent/tools.py`.
- Switch the agent system prompt to teach `search_filesystem`-first behavior.
- No data migration. v1's `meta.json` files are the v2 metadata store.

Single-doc tools stay available in v2 — they are still the right move when the agent already knows which document.

## Module layout

```
pageindex/filesystem/
├── __init__.py
├── store.py          # locate {pdf, json, meta.json} triples; load meta sidecars
├── virtual_nodes.py  # axis selection, clustering, tree projection
└── traversal.py      # descend / flatten policy; called per agent step
```

`agent/tools.py` v2 tools call into `filesystem.store` and `filesystem.virtual_nodes` to materialize the per-query tree, and into `filesystem.traversal` to pick the next descent step.

## Settings (added in Phase 3+)

| Setting | Default | Effect |
|---|---|---|
| `filesystem_meta_model` | `${llm_model}` | Model used to generate `.meta.json`. A cheaper model is fine. |
| `filesystem_axes_default` | `["category", "entities"]` | Axes considered when projecting query-dependent trees. |
| `filesystem_max_tree_depth` | `3` | Cap on query-dependent tree depth. |
| `filesystem_flatten_threshold` | `0.6` | LLM confidence below which traversal flattens instead of descending. |
| `filesystem_max_llm_hops_per_query` | `5` | Hard cap on traversal LLM calls per agent query. |

## Open questions

These are flagged for design-time decisions during Phase 4:

- **Clustering algorithm for virtual nodes** when metadata axes aren't enough — k-means on category embeddings, LLM-driven clustering, or a hybrid. Decide on a real corpus, not in the abstract.
- **Metadata schema versioning** — `schema_version` at the top of every `meta.json` lets us migrate lazily when v2 adds fields.
- **Latency budget per query** — adaptive traversal could in principle make many LLM calls. `filesystem_max_llm_hops_per_query` caps it; the cap value needs tuning on a representative corpus and is the most likely source of UX regressions.
